## 3. Notes on parameter compatibility (gpt-5-class)

The first smoke attempt failed with a `400 BadRequestError`:

> Unsupported parameter: `max_tokens` is not supported with this model. Use `max_completion_tokens` instead.

This is the documented break on gpt-5-class models (gpt-5, gpt-5.x,
o1, o3, o4-mini, …). The wrapper at
`product/evaluation/model_clients/openai_client.py` was updated so
that for any model whose name starts with `gpt-5`, `o1`, `o3`, or
`o4`, the request uses `max_completion_tokens` instead of
`max_tokens`. The retry succeeded with response_model
`gpt-5.4-mini-2026-03-17`.

The same wrapper treats `temperature=0.0` as "use the model default"
for those same model families (passing `temperature=0` to gpt-5-class
models is rejected with another 400). For backward compatibility,
gpt-4 / gpt-4o / gpt-3.5 models still get the explicit `temperature`
value.

## 5. What this lock guarantees

- All System B / OpenAI runs (smoke and full) for Stage R2-4A use
  `gpt-5.4-mini` as the request model and the wrapper's deterministic
  configuration above.
- The pinned response model `gpt-5.4-mini-2026-03-17` is what the API
  actually served at lock time; if a future run returns a different
  snapshot string, the run log surfaces it.
- If the model is ever withdrawn or the alias is repointed, the
  runner will continue to send `gpt-5.4-mini` and the run log will
  show the new resolved snapshot — no silent fallback.

## 6. Stop conditions

The wrapper does not silently fall back to a different model. If
`gpt-5.4-mini` is unavailable, the runner records the error on the
case's raw row (`raw.jsonl`) and the parsed row is marked
`parse_status="error"`. Aggregate counts in the run log surface this
clearly. Per the Stage R2-4A spec, an unavailable target model halts
the experiment.
